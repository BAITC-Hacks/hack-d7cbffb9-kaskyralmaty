## Утверждённый результат и границы

Основной сценарий: **MP3 → транскрипт с говорящими → поручения (кто / что / срок) и саммари → DOCX**. Результат показываем после завершения встречи. Сервис получает и хранит запись; агент разбирает стенограмму. Неизвестные исполнители и сроки не выдумываются, говорящий не обязательно является исполнителем.

Сразу после рабочего пути на MP3 добавляем запись в браузере: микрофон + звук выбранной вкладки/системы через getDisplayMedia и Web Audio, затем тот же конвейер обработки. Доступность звука зависит от браузера и выбранного источника. Если захват экрана не содержит аудиодорожки, интерфейс явно предупреждает об отсутствии звука встречи; запись только микрофона не выдаётся за полный захват. Полученный браузерный аудиоформат приводится к входу общего конвейера.

Перед стартом записи показываем баннер: **«Встреча записывается и транскрибируется ИИ, объявите участникам»**. Баннер просит секретаря уведомить людей, не считается автоматической доставкой уведомления участникам.

Для поручений показываем «скоро срок / просрочено» относительно даты встречи. Предлагаемое точное правило для этого плана: дата исполнения раньше даты встречи — «просрочено»; от даты встречи до трёх календарных дней включительно — «скоро срок»; дальше — «позже». Неуказанный или неоднозначный срок не получает выдуманную дату и автоматический статус просрочки. Дата встречи также служит базой для нормализации относительных сроков. Это статическая оценка по дате встречи, не автоматические напоминания по текущему времени.

Экспорт — DOCX. PDF допускается только при запасе времени после обязательных проверок и до заморозки кандидата. Казахские и смешанные тестовые записи предоставляет пользователь; для этапа 3 они нужны к 16:10.

Все модели работают локально/self-hosted. Brev принимается как «сервер заказчика» по решению пользователя; пользователь подтвердил, что vLLM с Qwen уже работает. Передача аудио и текста внешним облачным API не допускается.

## Утверждённый стек

Перенесён из раздела 4 HANDOFF по прямому решению пользователя; повторный выбор не проводится.

| Слой | Решение |
|---|---|
| Язык, зависимости | Python 3.11, uv, pyproject.toml и uv.lock |
| Сервис и интерфейс | FastAPI, одна HTML-страница |
| Основной ASR | faster-whisper large-v3 |
| Казахская речь | SeamlessM4T-v2-large для повторного распознавания казахских фрагментов |
| Диаризация | SpeechBrain ECAPA, эмбеддинги и кластеризация |
| Языковая модель | Qwen3.8-27B NVFP4 в vLLM на Brev |
| Агент | PydanticAI, схемы Assignment и Protocol, предметные инструменты |
| Экспорт | python-docx |
| Оценка | jiwer для WER, сравнение precision/recall поручений с эталонами |
| Развёртывание | docker compose на GPU-машине, ASR-сервис и vLLM |

Точные версии библиотек, образов и ревизии моделей фиксируем при реализации. Наличие языка на уровне записи не считаем доказательством языка каждого сегмента: способ выделения казахских фрагментов и качество на смешанной речи проверяем в этапе 3. Не обещаем точность из чужих измерений как результат на наших данных.

По последнему прямому указанию пользователя **основной путь README — docker compose на GPU-машине**. Это согласованное исключение из прежнего правила AGENTS.md о plain-командах как первом пути. Для экспертов без GPU предусмотрен отдельный режим воспроизведения результатов двух предоставленных MP3, без персональных аккаунтов и платных подписок.

## Проверяемость и доказательства

- scripts/check.sh клонирует репозиторий во временную директорию, выполняет точные команды соответствующего режима из README и проверяет основной сценарий. Режимы GPU и воспроизведения проверяются раздельно и обозначаются в выводе.
- GPU-проверка использует реальные ASR и LLM, ошибки моделей не превращаются в успешное воспроизведение. DOCX содержит результаты именно обрабатываемой записи.
- Воспроизведение использует заранее вычисленные результаты двух комплектных MP3 с указанием происхождения и связи с исходными файлами. На странице и в README написано: **«не проверка моделей»**. Произвольное новое аудио не выдаётся за обработанное в этом режиме.
- Эталонные DOCX используются для сравнения, не как скрытая замена результатов моделей. Отсутствие разметки или тестовой записи отмечается как отсутствие проверки, а не успешный тест.
- README обновляется на каждом этапе: что реализовано, архитектура, установка/запуск, пример проверки, данные/сервисы, ресурсы, сторонние компоненты, ограничения и развёрнутый адрес при наличии.
- Вывод команд сохраняется автоматически в docs/runs/. После завершённых задач — коммит, затем строка с его хешем в docs/LOG.md; не реже раза в час. Каждый закрытый этап завершается push. Пока scripts/check.sh не проходит, этапы 1–3 не закрываются.
- Секреты — только в .env, шаблон переменных — .env.example, .env исключён из git. Записи и результаты не отправляются сторонним API обработки.
